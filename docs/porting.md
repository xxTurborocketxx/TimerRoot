# Porting guide — TimerRoot on another device

TimerRoot is not a universal root. The exploit chain (CVE-2026-98260,
POSIX CPU timer use-after-free) is kernel-specific: every per-build
constant — the timer call site, the cred geometry, the struct offsets —
must match the running kernel, or the attempt can corrupt the kernel
instead of failing cleanly. This guide describes what a port realistically
takes: **Parse offsets** (no build, for new firmware builds of a
supported kernel), a **real port** (new profile, new device, same kernel
family) and a **research port** (other kernel versions entirely).

## 1. Is the device a candidate at all?

Hard requirements:

- arm64, Android 12+, a working [Shizuku](https://shizuku.rikka.app/)
  (the exploit runs as the shell user via a Shizuku user service);
- a kernel whose KMI never received the CVE-2026-98260 fix — check with
  `adb shell uname -r` and compare against the
  [supported list](../README.md#supported-devices);
- tracefs reachable from the shell domain (the trace oracle needs it).

Verified in this repo: vivo / iQOO devices on GKI `6.1.145` and the
Motorola Edge 50 Ultra on GKI `6.1.157` (`ctwo`). Everything with a
current security patch level that carries the timer fix is out, no
matter how good the offsets are.

## 2. Path A — Parse offsets (no build required)

This path covers a **new firmware build of an already-supported kernel**
— for example the next monthly patch of the Edge 50 Ultra, as long as the
kernel banner still says `6.1.157-android14-…`. It is not a way to port to
a different device.

1. Get the exact `boot.img` or a **full OTA package (.zip)** for *your*
   model and version. Full packages are extracted in-app (`payload.bin`,
   zip64 + zstd) and the package's device/version is compared against the
   phone first; mismatches are refused, and so are `init_boot` /
   `vendor_boot` images (no kernel inside).
2. In the app, tap **Parse offsets** and pick the file. On success it
   writes `/data/local/tmp/ic-syms.txt`.
3. Run the one-tap jailbreak as usual.

Kernel images other than `6.1.145` / `6.1.157` are refused — the parser
is only validated on those (Path C below is what a new kernel version
takes). If the run fails, save the log with the **Share** button (the
exported file is the ground truth; copy/paste from the log tab can
garble it) and report it in the
[XDA discussion thread](https://xdaforums.com/t/tool-timerroot-one-tap-root-for-motorola-edge-50-ultra-no-bootloader-unlock-vivo-iqoo.4808957/)
with device, `ro.build.display.id` and `uname -r`.

## 3. Path B — a real port (new device, same kernel family)

First check `uname -r` on the device: a device running the
**identical GKI image** (`6.1.157-android14-11-gb3d4cdadf339-ab16160610`)
is built in as of v0.31 — no port needed, any brand or model. For
requests outside that image, **Share a device report** in the About tab
collects the props a port request needs.

For a new device on `6.1.145` / `6.1.157` the core needs a per-build
profile. The pieces:

| File | Contents | How the values are derived |
| --- | --- | --- |
| `core/profiles.h` | per-build constants: timer call site, cred geometry, task/cred struct offsets, static symbol addresses | embedded kallsyms of the kernel Image (link-time, `_text` = `0xffffffc008000000`); call-site low21 bits by disassembling the Image (`core/tools/disasm_kernel.py`, `derive_offsets.py`); struct offsets from the Image's BTF; cred object/slab size measured on the running kernel |
| `core/anchors.h` | per-build anchor table: 66 link-time symbol addresses used by the spray hit-check (`{ kernel banner, models, version, table name, links }`) | generated by `core/tools/make_port.py row` from the Image's embedded kallsyms — fail-closed: the row is refused unless the four plan symbols (`__tracepoint_sys_exit`, `selinux_state`, `init_user_ns`, `init_cred`) resolve |
| `core/extra_syms.h` | fake-cred object symbols (`root_user`, `init_ucounts`, `init_groups`); on verified builds they sit at fixed deltas from `init_user_ns` (`+0x298` / `+0x1b48` / `+0x15b8`) | same embedded kallsyms; cross-check with `core/tools/verify_tables.py` against parsed symbol dumps |

Workflow:

1. Extract the kernel Image from the exact firmware of the target build
   (full OTA or `boot.img`).
2. Derive the profile constants for `profiles.h` (derivation notes in the
   file header and `core/README.md`) and add an
   `#elif defined(IC_PROFILE_…)` block with a `PROFILE_KERNEL_MATCH`
   substring — the core refuses kernels that do not match its profile.
3. Generate the build's anchor and fake-cred rows with
   `core/tools/make_port.py row IMAGE --kernel <banner>` (it also
   prints the measured fake-cred deltas and refuses rows with
   unresolved plan symbols), add them to `anchors.h` / `extra_syms.h`,
   and verify both with `verify_tables.py` against an independent
   symbol dump when one exists.
4. Build the static core with the Android NDK:

   ```sh
   cd core
   ./build.sh ../apk-gradle/app/src/main/assets/ic-timer ctwomoto
   ```

   `build.sh` passes `-DIC_PROFILE_<PROFILE>` and requires NDK r27 with
   API 29 (older NDKs emit an underaligned TLS segment that bionic
   refuses at exec time). Ship the binary as the app asset `ic-timer`.
5. Add the device to the supported list in the README, rebuild the app,
   and run the full chain on the device: trace oracle, cred leak, spray,
   write-verify, `LPE-PROOF`, then the ROOT-manager handoff. The
   write-after-verify read-back is mandatory — a profile that skips
   verification corrupts kernels instead of failing safely.

## 4. Path C — other kernel versions (5.10, 6.6, 6.18, …)

The timer UAF itself spans several kernel generations, and other ports
already exist as prior art:

- `kpgc10kai/TimerRoot` — same CVE on 6.6 and 6.18, BTF-derived offsets,
  stricter trace validation (`free_seen=1 + burst hit=1` before reaping);
- `nisu123f/dada-cve-AN00` — a 5.10.236-android12-9 profile (different
  cred geometry: `task->cred=0x780`, cred copy size 168);
- `whooslizi/infinitycore-x200pro` — a 5.10 chain variant with a
  pre-zombie free watcher.

Study those before writing anything. A new kernel version is a research
port, not an offsets port — several 6.1 assumptions stop holding:

1. **Slide derivation.** The trace oracle relies on
   `do_timer_create` sitting within the first 2 MiB of the image, so the
   low 21 bits of the call site give the KASLR slide
   (`slide = site0 - (0xffffffc008000000 + low21)`). On other kernels the
   function can sit elsewhere or the alignment differs — either verify
   the 2 MiB property from the Image or derive the slide from readable
   kallsyms / the de-tagged tracepoint instead.
2. **Page geometry.** 4K and 16K kernels have different spray and
   hit-check geometry; the anchor set itself (66 wait/allocation paths
   chosen for their timing behavior) must be re-checked, not just
   re-derived.
3. **Struct layouts.** cred and `task_struct` offsets shift between
   versions (BTF of the Image gives them), and the cred copy size in
   `prepare_creds` differs (0xb0 here, 168 on 5.10 builds) — measure
   `CRED_REQ` / `CRED_ALLOC` on the running kernel, do not copy values.
4. **Trace event layout.** The raw scan matches
   `type@i-8 / pid@i-4 / pfn@i / order@i+8` in the trace buffer; a
   different kernel can lay the fields out differently.

Workflow — **QEMU first, hardware last**:

1. Confirm the target kernel contains the vulnerable timer code and its
   KMI lacks the fix.
2. Boot the target Image under QEMU with the in-repo harness
   (`harness/qemu_core_init.c`: minimal init, mounts proc/sys/dev/tracefs,
   can drop to uid 2000, runs the core from the console log). The whole
   6.1 chain in this repo was developed exactly that way, including the
   shell-domain, policy-enforcing configuration (`IC_PROFILE_QEMU_IQOO12`
   is the reference profile).
3. Derive the profile, anchors and extra syms from that Image (same
   tools as Path B), fix the four version assumptions above, and iterate
   until the chain is green under QEMU end to end. Budget for slow
   attempts (~40 s each under QEMU).
4. Only then build for the device, add the profile gate, and test on
   hardware — with backups made, because a wrong assumption here
   corrupts kernels instead of failing safely.

## 5. Safety rules for everyone testing

- A panic on a locked bootloader is just a reboot — nothing is flashed,
  nothing is bricked. But an unclean shutdown can cost data: back up first.
- One exploit run per boot. After a failed run that holds a zombie
  (`burst missed; holding zombie` in the log), reboot before trying
  again — rerunning against a stale timer node can panic the kernel.
- Run on an idle system only; the app's load gate waits out boot storms
  for a reason.
- Prefer logs exported with the Share button over pasted log-tab copies.

## 6. Reporting results

Post device reports in the
[XDA discussion thread](https://xdaforums.com/t/tool-timerroot-one-tap-root-for-motorola-edge-50-ultra-no-bootloader-unlock-vivo-iqoo.4808957/):
device and model, `ro.build.display.id`, `uname -r`, the full exported
log, and what the app reported. Promising reports are how the supported
list grows — a new profile only lands in the repo after an end-to-end
verified run on real hardware (Path C: on QEMU *and* hardware).
